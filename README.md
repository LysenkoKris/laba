# Отчет по выполнению лабораторных работ (№1–7)

Проект представляет собой асинхронный REST API сервис, разработанный на стеке **Python 3.13 + Litestar + SQLAlchemy 2.0**. Приложение реализует архитектуру N-уровней (Controller, Service, Repository) и работает с базой данных **PostgreSQL**. Интегрированы брокер сообщений **RabbitMQ** и система кеширования **Redis**.

---

## Реализованный функционал (ЛР 1–5)

К текущему моменту выполнены следующие этапы разработки базового сервиса.

### 1. Архитектура и БД

* Спроектированы ORM-модели (`User`, `Address`, `Order`, `Product`) со связями One-to-Many и Many-to-Many.  
* Настроены асинхронные миграции (Alembic) и подключение к PostgreSQL через `asyncpg`.  
* Реализован паттерн **Repository** для абстракции работы с данными.  
* Реализован паттерн **Service** для бизнес-логики.  
* Внедрение зависимостей (DI) через механизм Litestar.

### 2. Тестирование (Лабораторная №4)

* Настроена среда тестирования на базе **pytest**.  
* Внедрена система **фикстур**:
  * изолированная тестовая БД (**SQLite in-memory**);
  * `TestClient` для интеграционных тестов API;
  * mock-объекты для изоляции unit‑тестов сервисного слоя.
* Написаны тесты для всех слоёв: модели, репозитории, сервисы, контроллеры.  
* Настроен отчёт о покрытии кода (`pytest-cov`).

### 3. Качество кода и Контейнеризация (Лабораторная №5)

* Настроены линтеры и форматтеры: **Black**, **Isort**, **Pylint**.  
* Внедрён **pre-commit** для автоматической проверки кода перед коммитом.  
* Написан **Dockerfile** для сборки образа приложения.  
* Написан скрипт **entrypoint.sh** для управления запуском и миграциями.  
* Настроен **docker-compose.yaml** для оркестрации сервисов (App + Postgres + pgAdmin).

## Запуск проекта через Docker

Это основной и рекомендуемый способ запуска, так как он поднимает всё окружение автоматически.

### 1. Подготовка

Убедитесь, что файл `entrypoint.sh` имеет права на выполнение:

```
chmod +x entrypoint.sh
```

### 2. Сборка и запуск

Выполните команду в корне проекта:

```
docker compose up --build
```

### 3. Доступ к сервисам

После успешного старта (в логах появится `Uvicorn running on http://0.0.0.0:8000`):

* **API приложения:** http://localhost:8000/users  
* **Документация (Swagger):** http://localhost:8000/schema/swagger  
* **pgAdmin (интерфейс БД):** http://localhost:5050  
  * *Логин/Пароль* см. в `docker-compose.yaml` (`admin@example.com` / `admin`).

### 4. Остановка

```
docker compose down
```

## Запуск тестов

Тесты можно запускать двумя способами: внутри Docker‑контейнера (рекомендуется) или локально.

### Способ 1: Внутри Docker (рекомендуемый)

1. Запустите контейнеры (если не запущены):

   ```
   docker compose up -d
   ```

2. Выполните команду запуска тестов внутри контейнера `web`:

   ```
   docker compose exec web pytest
   ```

   С отчётом о покрытии:

   ```
   docker compose exec web pytest --cov=app
   ```

### Способ 2: Локально (через venv)

1. Активируйте окружение:

   ```
   source .venv/bin/activate      # Linux/macOS
   .\.venv\Scripts\activate       # Windows
   ```

2. Запустите pytest:

   ```
   pytest
   ```

# Лабораторная работа №6 — Интеграция с RabbitMQ

В лабораторной работе №6 реализовано взаимодействие сервисов через брокер сообщений **RabbitMQ**, который разворачивается вместе с приложением в `docker-compose`.

## Инфраструктура RabbitMQ

RabbitMQ поднимается отдельным сервисом:

```
rabbitmq:
  image: rabbitmq:3-management
  container_name: rabbitmq-1
  ports:
    - "5672:5672"    # AMQP
    - "15672:15672"  # Web UI
  environment:
    RABBITMQ_DEFAULT_USER: guest
    RABBITMQ_DEFAULT_PASS: guest
    RABBITMQ_DEFAULT_VHOST: local
```

После запуска:

* веб‑панель доступна по адресу `http://localhost:15672`;
* логин/пароль: `guest / guest`;
* используется виртуальный хост `local`.

## Подключение к RabbitMQ

Для работы с очередями используется URL:

```
amqp://guest:guest@localhost:5672/local
```

## Как запускать и тестировать интеграцию с RabbitMQ

1. **Запуск инфраструктуры**

   ```
   docker compose up -d
   ```

2. **Запуск приложения**

   Приложение запускается тем же `docker compose up` (контейнер `web`), либо локально через `uvicorn`, если требуется.

3. **Запуск консьюмера**

   Из активированного виртуального окружения:

   ```
   python -m app.rabbit.consumer
   ```

4. **Отправка тестовых сообщений**
   
   Из активированного виртуального окружения:

   ```
   python -m producer
   ```
   

5. **Проверка результата**

   * в консоли консьюмера должны появиться сообщения вида `[product] received: {'msg': 'test'}`;
   * в панели RabbitMQ в разделе **Queues** видно движение сообщений по очередям `product` и `order`.

# Лабораторная работа №7 — Использование Redis и кэширование

В лабораторной работе №7 в проект был добавлен **Redis** и реализовано кэширование запросов к данным пользователя с последующей очисткой кэша при изменении или удалении записей.

## Инфраструктура Redis

Redis разворачивается в `docker-compose` как отдельный контейнер:

```
redis:
  image: redis/redis-stack:latest
  container_name: redis
  ports:
    - "6379:6379"
  volumes:
    - redis-data:/data
```

После запуска:

* с хоста Redis доступен по адресу `localhost:6379`;
* из контейнера `web` — по хосту `redis` и порту `6379`.

## Примеры работы с Redis

Для демонстрации типовых операций создан модуль `app/redis_examples.py`, который показывает работу со строками, счётчиками, списками, множествами, хэшами и отсортированными множествами.

Запуск примеров:

```
docker compose up -d      # если инфраструктура ещё не запущена
python -m app.redis_examples
```

В консоли выводятся результаты выполнения команд (`PING`, чтение/запись ключей и т.д.), что подтверждает корректное подключение к Redis.


## Как тестировать Redis и кэш

1. **Запустить инфраструктуру:**

   ```
   docker compose up -d
   ```

2. **Выполнить два подряд запроса к одному и тому же пользователю:**

   ```
   Invoke-WebRequest http://localhost:8000/users/<id>
   Invoke-WebRequest http://localhost:8000/users/<id>
   ```

   или аналогичные запросы через `curl`/Postman.

3. **Посмотреть логи контейнера `web`:**

   ```
   docker compose logs -f web
   ```

   * первый запрос — идёт в БД, лог `from cache` отсутствует;
   * второй запрос — в логах появляется строка `from cache`, что означает отдачу ответа из Redis.

4. **Проверить ключи в Redis (опционально):**

   ```
   docker compose exec redis redis-cli KEYS "user:*"
   docker compose exec redis redis-cli GET "user:<id>"
   ```

5. **Проверить, что кэш очищается:**

   * выполнить `PUT /users/<id>` или `DELETE /users/<id>`;  
   * убедиться, что ключ `user:<id>` пропал:

     ```
     docker compose exec redis redis-cli KEYS "user:*"
     ```

   * следующий `GET /users/<id>` снова читает данные из БД, а повторный — из кэша.
